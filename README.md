# CodeViva

### Don't detect the AI. Verify the understanding.

**An adaptive, AI-powered technical defence for university coding projects.**

## The problem

Generative AI can now produce complete programming projects in seconds. At the same time, AI-code detectors cannot reliably determine who wrote a piece of code: correct implementations are often structurally similar, and detector results are too uncertain for high-stakes academic decisions.

This leaves educators with the wrong question:

> **“Was this code generated by AI?”**

CodeViva asks a more useful and defensible question:

> **“Can the student demonstrate that they understand what they submitted?”**

Traditional project vivas can answer this, but manually reviewing every repository, preparing personalised questions, and interviewing every student does not scale.

## Our solution

**CodeViva** transforms a submitted codebase into a personalised, adaptive technical defence.

The platform analyses the student's repository, maps its implementation to course learning outcomes, and conducts a short real-time assessment containing:

- Questions about the student's own architecture and design decisions
- Code-tracing and prediction exercises
- Data structures and algorithms questions grounded in the project
- Debugging and edge-case challenges
- A small live modification to the submitted code
- A related transfer task that tests whether the student can apply the concept elsewhere

Educators receive a traceable evidence report showing what the student could explain, reason about, modify, and apply. CodeViva does **not** produce an AI-generation probability or automatically accuse a student of misconduct.

## How it works

```text
Submit repository
       ↓
Map files, symbols, dependencies and concepts
       ↓
Connect project features to learning outcomes
       ↓
Generate a grounded assessment plan
       ↓
Run an adaptive viva and practical task
       ↓
Produce an evidence-based educator report
```

### 1. Repository analysis

CodeViva identifies the project's structure, important functions, algorithms, dependencies, tests, and potential edge cases.

### 2. Assessment planning

The system creates project-specific questions tied to lecturer-defined learning outcomes. Every generated question contains a verified reference to relevant code.

### 3. Adaptive defence

The examiner adapts to the student's responses:

- A strong response leads to a deeper question.
- A partial response triggers a targeted probe.
- An incorrect response leads to a trace or prediction task.
- An unclear response is rephrased once.

### 4. Practical verification

Students debug, modify, or extend part of their project and complete a small related DSA problem. This tests application and transfer rather than memorised explanations alone.

### 5. Evidence report

Instead of a black-box score, lecturers receive the question, response, code reference, follow-up, system observation, and confidence behind every suggested judgement.

## Assessment dimensions

| Dimension | Evidence collected |
| --- | --- |
| Code navigation | Locates and explains relevant components |
| Control and data flow | Traces execution and predicts behaviour |
| Design reasoning | Justifies architecture and trade-offs |
| DSA knowledge | Explains algorithms, data structures, and complexity |
| Debugging | Diagnoses defects and edge cases |
| Modification | Safely changes the submitted implementation |
| Concept transfer | Applies knowledge to a related problem |
| Testing | Designs and interprets meaningful tests |

## Prototype scope

For the hackathon, we are deliberately keeping the first version focused:

- Python repositories
- Small DSA and software-engineering projects
- GitHub URL or ZIP submission
- A clean upload-first ingestion experience
- Fast repository analysis and chunking for retrieval
- Stored code context for later grounded assessment generation
- A reviewable foundation for future educator evidence reports

### Core student journey

1. Submit a repository
2. Review the assessment briefing
3. Complete the adaptive project viva
4. Complete a live code task
5. Submit evidence for educator review

### Core educator journey

1. Define learning outcomes and a rubric
2. Review generated assessment material
3. Inspect evidence by criterion
4. Confirm, amend, or escalate each judgement

## Responsible assessment

CodeViva is designed as an assessment-support tool—not an automated misconduct detector.

- No “AI-written” or “cheating probability” score
- No automatic disciplinary decisions
- Human review for consequential outcomes
- Evidence attached to every suggested judgement
- Multiple response modes and accessibility accommodations
- Student communication style separated from technical competence
- Repository contents treated as untrusted input
- Submitted code never executed without strict sandboxing
- Course material and lecturer-defined outcomes used for grounding
- Clear distinction between observation, inference, and uncertainty

## Why it matters

The future of programming education cannot depend on perfectly detecting every use of AI. Students will increasingly build software with intelligent tools, but universities still need to verify that learning has occurred.

CodeViva makes that verification scalable:

- **Students** receive a fair opportunity to demonstrate understanding.
- **Educators** spend less time preparing individual vivas.
- **Universities** receive stronger evidence than unreliable AI detection can provide.
- **Assessment** shifts from code authorship to explainable, applicable knowledge.

## Hackathon

CodeViva is being developed for **Reply AI on Campus**, part of the Reply Student Tech Clash.

The challenge asks teams to identify a real problem in university teaching, learning, or assessment and build an AI-based solution. CodeViva addresses a growing assessment problem created by AI-assisted software development while keeping educators in control of high-stakes decisions.

## Current build: ingestion-first MVP

This repository now includes the first implementation slice for CodeViva:

- **Frontend:** React + Vite upload-first landing page
- **Backend:** FastAPI ingestion API
- **Storage:** PostgreSQL with pgvector-ready schema
- **Pipeline:** GitHub or ZIP intake, repository normalization, file inventory, chunking, and summary generation
- **Containerization:** Docker Compose for local full-stack development

### Run locally with Docker

```bash
docker compose up --build
```

Then open:

- Frontend: `http://localhost:5173`
- Backend docs: `http://localhost:8000/docs`

### Backend development without Docker

```bash
cd backend
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload
```

### Frontend development without Docker

```bash
cd frontend
npm install
npm run dev
```

## Success criteria

The current ingestion MVP succeeds if it can:

1. Accept a GitHub repository URL or ZIP archive.
2. Analyse a real student repository.
3. Extract file metadata and dominant project signals quickly.
4. Chunk source files and docs for later retrieval.
5. Persist repository context for future grounded assessment generation.
